# Scrolling performance audit

## Scope and baseline

This is a **static HTML/CSS/JavaScript site**, not a React app. There are no React state updates, render cycles, image/video streams, card-position RAF loops, or scroll-driven parallax to remove. All production frontend changes are in `index.html`.

The supplied working copy already had passive/RAF scroll scheduling, cached section geometry, IntersectionObserver reveals, temporary reveal `will-change` hints, offscreen animation pausing, transform-based card effects, a transform-based CTA gradient, reduced-motion CSS, and the Discovery Call CTA. Those features were preserved, not claimed as newly implemented.

There was no Git repository. An unchanged baseline was saved before editing:

- Baseline file: `/tmp/aigrow-scroll-profile/baseline/index.html`

## Evidence and changes

### Scroll-handler forced layout

Chrome Performance traces attributed synchronous `Layout` and style recalculation events to `updateScrollEffects`, specifically its `window.scrollY` read. Caching section positions did not prevent that read from flushing pending animation/style/overflow work. This was forced layout in a JS callback, not a repeated top/left mutation on the creator cards.

The modern-browser path now has **no per-scroll JavaScript handler**. Empty, nonpainting IntersectionObserver ranges handle the 40px header threshold, 600px back-to-top threshold, and navigation sections. They extend from document top to each threshold so that jumps across entire sections are detected, including backwards navigation. Geometry is measured in one read batch only on initial load, resizing, font completion, or actual document size changes. Scroll progress stays on the existing CSS scroll timeline.

Browsers without scroll timelines, and the reduced-motion progress indicator, retain one passive, coalesced RAF fallback. That fallback has no per-frame section measurements. Browser checks cover both fallback paths and live preference changes.

### Visually redundant reveal transitions

`finishReveal` removed the temporary layer hint and changed the completed transform to `none`, while the element still had a 700ms transform transition. Chrome recorded a second transform animation on already-revealed blocks (`process-canvas in revealed`, selection board, etc.).

`[data-r].in.revealed` now also sets `transition: none`. The visible entrance keeps its original distance, scale, easing, and 700ms duration. Only the visually redundant cleanup transition is removed. Card rotations, hover displacement, colors, typography, shadows, and responsive placement are unchanged. No additional permanent `will-change` hints were added.

A CSS-only diagnostic removed the redundant cleanup transitions and reduced paint-event counts, but did **not** eliminate every layout or paint event. Do not attribute all form painting to that one bug.

### CTA gradient geometry

The original moving pseudo-element was 200% wide and 200% high, with its top at -50%. It is now 200% wide and 100% high, with a **static** `background-size: 100% 200%` and centered vertical background position. This renders the same crop of the same gradient and keeps the same horizontal translation, 8-second duration, and easing.

The animated element's geometric area is halved. This is **not** a claim that total measured GPU memory or raster time fell by 50%: Chrome can tile and cull layers, and CPU throttling does not emulate a weaker GPU. The oversized text, base green, isolated decoration, clipping, and offscreen phase-preserving pause remain intact.

### Other audited effects

- Grain overlay: static SVG noise, not regenerated by application JS during scrolling; no grain paint hotspot in the captured workload. Preserved.
- Hero: transform/opacity floating cards, orbit, ambient gradient, static-blur crossfade; existing offscreen pause preserved.
- Creator Selection: no layout-property animation or card-position JS loop. Existing board entrance and individual card hover transforms preserved.
- Header: backdrop blur and shadows retained. No evidence justifying a visual downgrade or blanket promotion.
- Hover-only shadow/color/padding effects outside the target section remain; they are not continuous scroll-state updates. This audit does not claim every interaction is compositor-only.
- Counters: existing finite 1.6-second RAF counters update text only when its value changes, finish offscreen, and respect reduced motion. They are not card-motion loops; their numeric text can cause layout while counting.
- Fonts: waited for `document.fonts.ready` before measured scrolling, separating late font layout from scrolling cost.
- Extra trials (form wrapper, removing form layout containment, changing contact overflow clipping, 3D-only form reveal, removing native control appearance) did not materially reduce remaining layout counts and were discarded.

## Benchmark method

`tools/profile-scroll.mjs` uses the **Chrome DevTools Protocol Performance/Tracing APIs**, CPU throttling, and real synthesized scroll gestures. It is not a Lighthouse page-load score and is not a React render-count proxy.

Environment: Apple M2, 16GB RAM, Chrome 154.0.8037.93, Metal/ANGLE hardware GPU compositing. A local static server serves immutable before/after snapshots. Playwright was reused from an existing local installation; no application dependencies were added.

For each configuration, three warm-cache measured navigations per revision in headless Chrome. The repeated matrix uses synthesized wheel/mouse-source scrolling on desktop and touch-capable mobile/tablet viewports. Additional **touch-source** and visible/headed Chrome runs are reported separately, not mixed into the repeated-run medians:

1. Wait for fonts and startup animation completion.
2. Land just before Creator Selection, keeping its entrance untriggered until the gesture.
3. Scroll down through all five creator cards, solutions/FAQ, neon CTA and Discovery Call form at 1,800 CSS px/sec.
4. Reverse through the same area, then scroll down again.
5. Record the trace, CDP task/script/layout metrics, RAF intervals, long tasks, synchronous layout stack attribution, and Chrome dropped/partial-frame trace events.

Before and after use the baseline scroll distance at each viewport, including on small mobile where the improved submit button changes the form height slightly. Tests run serially, not in competing browser processes. Main-thread time includes benchmark/trace overhead; raw timeline event sums can be nested, so task time comes from CDP `Performance.getMetrics`, not adding Paint + Layout + FunctionCall together.

Frame intervals from RAF are a **responsiveness proxy**, not proof that every composited frame was presented. Chrome partial/dropped-frame events are reported separately. Small timing changes on a shared M2 should not be generalized to every device.

## Results

Individual runs, including ranges/outliers, are in [`performance-results.json`](performance-results.json). Each number below is the median of three identical-distance runs, approximately 7.5–7.9 seconds per run. Values are **milliseconds**, except event counts.

| Profile | Main-thread time, before → after | Script time, before → after | JS-forced layouts, before → after | Paint events, before → after |
| --- | ---: | ---: | ---: | ---: |
| Desktop 1440×900, 1× CPU | 799.7 → 734.5 | 48.0 → 21.0 | 47 → 0 | 260 → 231 |
| Desktop 1440×900, 4× CPU | 637.8 → 559.0 | 28.0 → 10.7 | 47 → 0 | 255 → 233 |
| Desktop 1440×900, 6× CPU | 881.3 → 811.2 | 33.8 → 11.8 | 47 → 0 | 256 → 231 |
| Mobile 393×851, DPR 2, 4× CPU | 479.4 → 458.5 | 24.2 → 15.4 | 39 → 0 | 166 → 148 |
| Mobile 393×851, DPR 2, 6× CPU | 736.4 → 676.0 | 32.9 → 13.5 | 40 → 0 | 167 → 152 |
| Tablet 768×1024, DPR 2, 6× CPU | 799.6 → 736.4 | 36.3 → 14.0 | 42 → 0 | 213 → 195 |

Interpretation:

- The structural result is consistent: **zero JS-attributed forced layouts** in every after run, with no ordinary-motion scroll RAF handler. This is not a claim of zero browser layout work.
- Script time fell approximately 36–65%; paint-event counts fell approximately 8–11%. Main-thread medians fell approximately 4–12%. The mobile 4× task-time ranges overlap, so that small total-time difference is not a demonstrated gain by itself. Early exploratory runs were much noisier; their larger apparent gains are deliberately not used here.
- **No >50ms long tasks** occurred during either baseline or candidate measured scrolling. That target was already met on this machine before the changes.
- Desktop/mobile RAF p95 was approximately **16.7–16.8ms** before and after. No desktop/mobile RAF gaps exceeded 25ms in the repeated matrix. This is consistent with approximately 60Hz callback cadence, not proof of presented 60 FPS on weak hardware.
- **Tablet is a remaining limitation:** baseline had 12 intervals above 25ms per pass; candidate had 11, with maxima around **33.4ms**. This is not a meaningful zero-jitter result. Trace partial-frame events also remain, and some runs still have two non-partial dropped-frame events. No universal/no-dropped-frame claim is justified.
- Remaining layout/paint work includes the form entrance (the invalidation trace identified about 43 form style/layout invalidations during its initial reveal) and one-time reveal/layer cleanup. Removing the synchronous JS reads lets the browser schedule that work rather than forcing it inside the scroll callback; it does not make all native form rendering free.

### Touch and visible-browser cross-checks

One additional before/after pair per touch profile used `SCROLL_INPUT=touch`: mobile at 4× and 6×, tablet at 6×. Mobile RAF maxima stayed at 16.8ms, with no >25ms intervals and no long tasks. Tablet again had 12 → 11 slower intervals, maximum 33.4ms. These are smoke checks, not additional repeated-run medians.

One visible/headed Chrome mobile-6× pair also completed: script time 40.4 → 19.4ms, forced layouts 39 → 0, no long tasks, RAF p95 17.5ms on both versions. Total main-thread time was essentially unchanged (827.2 → 835.1ms). This smoke pair used end-anchor-based distances differing by 21px after the CTA sizing change, unlike the fixed-distance repeated matrix; it is not a fair total-time benchmark or proof of a total-time gain.

### Design and functional checks

- **122 browser assertions passed** at 1440, 768, 393 and 320px widths: card count/rotation/hover, reveal cleanup, active navigation through large jumps, resize/FAQ changes, mobile menu, reduced-motion changes, unsupported-timeline fallback, native required-field validation, form payload, success/error feedback and duplicate-submit guard.
- **16 Python tests passed** for server-side recipient preservation/deduplication, all five fields in one Resend request, missing/invalid configuration, provider failures, API validation, private-file access and persistence statuses. Python 3.14 reports pre-existing unclosed SQLite connection `ResourceWarning`s in application database paths; they were not suppressed or refactored as part of this frontend task.
- `node --check` passed for all three `.mjs` tools. This static/Python project has no npm build or TypeScript typecheck configured.
- Creator Selection screenshots are **pixel-identical** at 1440, 768 and 393px widths with matching animation phases.
- CTA captures at 0, 2 and 4 seconds of the gradient cycle differ by at most **1/255 per RGB channel** on desktop/tablet and **2/255** on mobile (static-gradient raster rounding and the deliberately larger small-screen CTA). Typography/card positioning did not change. The comparison hides only the progress bar and freezes motion at matched phases; normal motion is checked separately.
- The full-width Request a Discovery Call button now keeps its 20px padding/1rem type below 400px, where the generic small-button rule previously overrode it. All five fields, supporting line and privacy text remain. Supporting/privacy descriptions are connected to the button, and field autocomplete/length constraints align with backend validation.

**Conclusion:** measured forced-layout and redundant-animation issues were fixed without flattening the design. CPU work and gradient geometry were reduced. The strict no-jitter target is **not fully verified**, particularly the tablet 6× case and physical low-end GPUs.

## Reproduce

Browser tools need Node and an existing Playwright installation with Google Chrome. Either make `playwright` resolvable normally, or set `PLAYWRIGHT_MODULE` to its absolute `index.mjs` path. The audit used:

```sh
export PLAYWRIGHT_MODULE='/Users/anuragkeshav/Documents/its a web project/node_modules/playwright/index.mjs'

# Production server for normal local testing (do not fill credentials for synthetic tests).
python3 backend/app.py

node tools/check-site.mjs http://127.0.0.1:8000
node tools/profile-scroll.mjs http://127.0.0.1:8000 /tmp/aigrow-new-mobile6 mobile 6 3
# Other profiles: desktop 1, desktop 4, desktop 6, mobile 4, tablet 6.
# Optional: HEADED=1 for visible Chrome; PROFILE_INVALIDATIONS=1 for detailed attribution.
# SCROLL_INPUT=touch switches the reproducible default wheel workload to touch gestures.
SCROLL_INPUT=touch node tools/profile-scroll.mjs http://127.0.0.1:8000 /tmp/aigrow-touch6 mobile 6 3
```

For a fair before/after comparison, serve two frozen directories with the same server. Set `SCROLL_DISTANCE` to the baseline summary's `results[0].route.distance` for both versions. Never submit real leads in a performance workload.

```sh
node tools/compare-visuals.mjs BEFORE_URL AFTER_URL /tmp/aigrow-visuals
python3 -m unittest discover -s backend -p 'test_*.py'
```

`check-site.mjs` intercepts form requests and exercises success, failure, validation, duplicate-submit guarding, reduced motion, responsive cards, navigation jumps, and geometry changes. It **does not send email**. Backend tests mock Resend and bypass private `.env` loading.

Raw local artifacts are under `/tmp/aigrow-scroll-profile/`; recorded traces were compressed to `trace-*.json.gz` after testing to reduce disk use. Load them in Chrome DevTools → Performance → Load profile (decompress first if needed). These temporary files are not part of the production deployment. The profile server was stopped after verification; restart a server before reopening the local URLs.

## Release limits

CPU-throttled mobile/tablet emulation is not a physical low-end Android/iPhone test, and no GPU/memory throttle was applied. Safari/iOS and actual weak hardware still need a release spot-check. Do not claim universal 60 FPS or zero dropped frames from the RAF samples alone.

Email routing is separately covered in `README.md`. The additional second recipient remains unconfigured until its actual address is supplied. Live credentials, sender verification and inbox delivery were not tested, and no live test emails were sent.
